# Catalog latency and memory on local NVMe

Measured October 7, 2026. These are sequential, low-load measurements of the implemented engine on one workstation. **No speedup, saturation throughput, cold-cache recovery or power-loss certification is claimed.**

## Workload and reproduction

- Rust 1.89.0 (`29483883e`), optimized bench profile, thin LTO, one codegen unit, no external crate dependencies.
- Engine source SHA-256: `5d280e4b00724f7a8099459cfee722d15ab403a0eda8fdc59821b7ff75c98221`, computed over sorted `crates/skrin/src/*.rs` path/NUL/content/NUL concatenations. Harness SHA-256: `be18c3c20769dcf95216bc29a85dbf64d78ac8d76edc38a2081d599dc12be450`.
- Intel Core i5-1035G7, four cores/eight logical CPUs; 7.3 GiB RAM visible. Linux `7.2.5-3-omarchy` x86_64. Scratch under the user's local `.cache`, on `/dev/mapper/root` btrfs (`compress=zstd:3`, `ssd`). The backing NVMe reports `KBG40ZNS256G TOSHIBA MEMORY`, 238.5 GiB. This machine's `/tmp` is tmpfs and **was not used for these measurements**.
- No CPU affinity, frequency control, cache eviction or exclusive access to the workstation. Background applications and swap are present. Flush completion has the conditional Linux/filesystem/device contract documented in [durability](../durability.md); this workload does not validate device behavior during power loss.
- 10,000 Accounts: a 29-byte unique email and u64 balance, seeded in 100-row synced commits. Every measured transaction uses the same mandatory `sync_all` boundary. Rows/indexes remain resident in RAM.
- Two-row workload: 1,000 transactions each updating keys `n % rows` and `(n + 1) % rows`, with equal/opposite balance changes. Plain `Database<Account>`, a catalog without indexes, and a catalog with unique email plus non-unique balance indexes all use the same native record values and final changes.
- Transfer workload: 1,000 separate transactions debiting/crediting two accounts and inserting an operation-ID Transfer record. This writes **three rows** and is not an equivalent two-row workload.
- Three independent processes per mode, in rotated order: plain/unindexed/indexed; indexed/plain/unindexed; unindexed/indexed/plain. Results are verified outside timed regions. [All per-process output](catalog-2026-10-07.txt) is retained, including latencies, transaction rates, warm reopen, checkpoint and process RSS.

```sh
cargo +1.89.0 bench -p skrin --bench catalog --no-run --locked
cargo +1.89.0 bench -p skrin --bench catalog --locked -- /local/btrfs/scratch 10000 plain
cargo +1.89.0 bench -p skrin --bench catalog --locked -- /local/btrfs/scratch 10000 unindexed
cargo +1.89.0 bench -p skrin --bench catalog --locked -- /local/btrfs/scratch 10000 indexed
```

For repeated runs, execute the built catalog benchmark directly to exclude compiler work and rotate the order above. Each process creates/removes its own unique directory under an already-existing scratch parent. Run on the filesystem/device being studied; an existing directory on tmpfs does not become physical durable storage merely because its path was passed to a synced workload.

## Results and limits

The table reports the **median of three per-process statistics**. Its p95/p99 columns are medians of each process's 1,000-sample percentile, not percentiles of a pooled 3,000-sample concurrent-service dataset. Transaction rate is measured transactions divided by the sum of timed transaction durations, excluding seed, verification and maintenance.

| Sequential workload | Median process p50 (ms) | Median process p95 (ms) | Median process p99 (ms) | Median process tx/s |
| --- | ---: | ---: | ---: | ---: |
| Plain two-row synced | 15.954 | 20.913 | 99.727 | 61.427 |
| Catalog two-row, no indexes | 16.997 | 26.223 | 54.270 | 50.196 |
| Catalog two-row, two indexes | 15.533 | 24.852 | 151.449 | 51.560 |
| Catalog transfer, two indexes + operation ID | 14.414 | 20.800 | 37.107 | 67.047 |

Per-process p50 varies materially: 9.525–16.429 ms for plain commits, 10.611–18.929 ms without indexes, and 14.988–18.497 ms with indexes. The indexed two-row p99 reaches 234.016 ms in one process. These sync-dominated, non-exclusive runs do not isolate CPU/index overhead or support a claim that additional index/row work is faster. They establish a reproducible real-filesystem baseline and expose tail variability that a tmpfs smoke test would hide.

Linux `/proc/self/status` VmHWM ranges:

| Whole process | Peak resident memory (KiB) |
| --- | ---: |
| Plain | 4,240–4,304 |
| Catalog without indexes | 4,812–4,940 |
| Indexed catalog + transfer workload | 8,812–9,072 |

The indexed process also contains 1,000 Transfer rows and checkpoint/recovery index reconstruction; its high-water mark is **not** a pure per-index allocation measurement. Plain includes checkpoint/reopen; unindexed measures only its two-row phase. Native allocator accounting, enforced process-memory budgets and memory behavior with pinned readers are separate remaining work. Each process has one database at a time; this harness does not include a second resident live backup.

Plain 10k-row checkpoint pauses range 70.168–106.344 ms and warm reopen 12.359–17.302 ms. Indexed 11k-row checkpoint pauses range 132.503–190.712 ms and warm reopen 19.238–35.212 ms. Those datasets and verification/index work differ; do not present the pause difference as a like-for-like optimization comparison. No caches were deliberately evicted.

Debug/release reference-model, index-constraint, independent-fixture, short-write/sync, persistence-projection and process-exit tests accompany these measurements. Green tests plus this benchmark do not close the real-device power-cut, platform-flush and native-resource gates in issues #3/#5, or deliver snapshot readers/group commit from #7.
